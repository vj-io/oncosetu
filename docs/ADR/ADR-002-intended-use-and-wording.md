# ADR-002: Intended use and the wording that keeps OncoSetu a records tool

Status: proposed · 8 Nov 2026 · **regulatory review pending · legal review pending** (no sign-off has been given; see
"Reviews" below) · Requirements: PRD §6.6, §10.4 (CDSCO row), FR-RAD-04, FR-REQ-01, FR-CON-07, FR-VOX-06

## Context

PRD §6.6 and §10.4 cite "ADR-002" as the place where the intended-use analysis and the request-letter legal review are
recorded. This file is that record. It restates the PRD's own text; it adds no regulatory claim of its own.

CDSCO's Medical Device Software guidance (CDSCO/MD/GD/MDSW/01/2026, 21 Jul 2026) has a single "MDSW" category and
turns on **intended medical purpose**; it excludes general wellness software. The PRD's reading (§10.4): records
organisation with provenance is likely outside its scope; a Missing-Record Radar worded as care gaps would not be. That
reading is the team's, not a regulator's or a lawyer's (§10.4 is headed "not legal advice; confirm with counsel before
pilot").

The IMC (Professional Conduct, Etiquette and Ethics) Regulations 2002, Reg. 1.3.2, give a physician's duty to issue
indoor-patient records within 72 hours of a request. Per §10.4 it is enforced through a State Medical Council or a
consumer commission and is not directly enforceable against hospitals under the Regulations. FR-REQ-01 requires the
request letter's template text to be reviewed by a health-law advisor before the pilot, with the review recorded here.

## Decision

### 1. Intended-use statement (PRD §6.6, draft for CDSCO and ethics review)

> "OncoSetu is records-management software that stores, organises and displays documents and patient statements
> provided for a person receiving cancer care, links each displayed item to its source, identifies source documents
> that are referenced but absent from the file, and supports authorised people in verifying, sharing and requesting
> records. It does not diagnose, stage, predict, risk-score, interpret images or results, recommend or alter treatment,
> or calculate doses. All clinical decisions are made by qualified professionals using the source documents."

The statement is shown on the landing page and is the reference for every feature decision: a feature that needs
wording outside it changes this ADR first.

### 2. Hard rules (PRD §6.6) and where the code enforces each

| Rule (PRD §6.6) | Enforcement in the prototype |
|---|---|
| No derived clinical attributes in the data model (§7) | The evidence gate rejects forbidden fields (stage, grade, response, progression, risk, dose, diagnosis, prognosis, recommendation, plan, impression, …) and keys outside each event type's allow-list: `src/core/gate`, `gate.test.ts` "forbidden field". Quote-only lines (stage, impression, margins, markers, addendum, regimen, diagnosis, history as written) are rule-extracted verbatim text, staff-only (`STAFF_ONLY_EVENT_TYPES`, `src/core/types.ts`) |
| No ordering of the ledger by clinical importance; category then date | `diffLedger` orders by category, then date (initial record: document-type priority, an administrative order) — `src/core/ledger` |
| No "progression", "worse", "urgent", "abnormal" generated by the system; source words with them only inside a quote | Copy lint: the `radar` list on every patient catalogue (`src/i18n`, `copy-lint.test.ts`) and the `judgement` list on every string literal and JSX text of `src/app` and `src/components`, staff screens included (`ui-lint.test.ts`, allowlist with reasons). Quote-only lines render inside `<q>` on the ledger and timeline. PRD also names a red-team evaluation as an enforcement: the red-team document set is built separately (W4, 8 Nov 2026) |
| The Radar speaks only about documents: "<document type> not in file for <event> documented on <date> (<source>)"; never a care step; "document-completeness checklist", not "care gaps" | Rule wording templates pass the `radar` and `legal` lint in English and Hindi (`radar.test.ts`); every rule starts in shadow mode until a clinician reviews it (`rules.yaml`, `/admin/rules`) |
| Every shared or printed output is headed "Document index, not a clinical summary" and lists the documents not in the file | Share payload and viewer, printable passport (`src/server/shares/payload.ts`, `src/i18n/shares.ts`, `src/app/print/passport`), with the FR-PAS-03 sentence "This summary contains only records provided to {brand}". Request letters ask for records and carry no record content, so they have no index heading |

### 3. Request letters (FR-REQ-01)

The letter refers neutrally to the patient's right to records ("the regulations provide for indoor records to be
issued within 72 hours of a request"), never claims a legal deadline binds the institution, never threatens action,
and is scoped by default to discharge summaries, inpatient records and pathology and imaging reports. The banned
phrases ("must", "legally required to", "within 72 hours you") are linted (`LEGAL_BANNED`, `letter.test.ts`).

### 4. Re-review triggers

This ADR is re-reviewed (PRD §6.6, §10.4): on every Radar rule change; on every feature change that adds wording a
patient, caregiver or outside doctor reads; and before the pilot.

## Consequences

- Wording is a controlled surface: a new screen string that trips the lint either changes or goes on the allowlist
  with a written reason, visible in review.
- The intended use limits the roadmap: features that would interpret, rank or recommend are out of scope unless this
  ADR, and the reviews above, are redone first.
